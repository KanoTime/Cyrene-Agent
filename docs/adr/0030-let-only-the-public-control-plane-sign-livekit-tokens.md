# 仅由公网控制面签发 LiveKit Token

正式异地配对流程的 LiveKit API Secret 只保存在公网控制面的 Secret 管理中，由控制面在接受 Call Request 后分别为一个移动设备和一个桌面实例签发每通电话专用、短期、限定房间与身份的 LiveKit Token。每个 Token 的初始加入有效期为 5 分钟；手机只能发布麦克风并订阅桌面音频和状态数据，桌面只能订阅该手机并发布角色音频和必要状态数据，双方都没有房间管理权限，房间及身份结束后永不复用。手机、桌面正式远程流程、数据库、日志、错误信息和审计记录都不得持有或暴露该 Secret；当前桌面设置中的 Secret 仅属于既有本地实验流程，正式迁移后应移除或明确隔离为开发模式，不能形成生产双写。Owner 负责云账号、LiveKit 项目及 Secret 轮换：怀疑泄露、账号异常、权限变化或供应商要求时立即轮换，无事件时至少每 12 个月轮换一次；先部署并验证新 Secret，再废止旧 Secret，旧 Secret 的退役不得超过单通电话 4 小时上限。审计只记录 key 标识和轮换时间，不记录 Secret。这样 Secret 泄露时可以在 LiveKit 与控制面集中轮换，无需重新发布移动应用。

“Device Revocation 必须立即结束整通电话”不能由 5 分钟初始加入 TTL、Token 刷新或仅删除房间替代：控制面先原子封住该 Voice Call 的 grant 领取和后续签发，再对本通随机房间的两个 call-scoped participant identity 都请求已选媒体服务的身份级撤销，并只在服务确认后删除最小房间/identity 映射；`DeleteRoom` 只能辅助断开当前其余参与者，不能替代 identity 级 token 截止。当前已核验的候选中，只有 LiveKit Cloud 的 `RemoveParticipant` 具有公开的旧 token 撤销边界，且 Cloud 调用失败时只允许保留短时、fail-closed 的 Media Revocation Work Item 并重试/显式处置，不能把本地 `ENDED` 写成“媒体已确认停止”，也不能重新签发资料或恢复通话；在服务确认前它仍占用 Owner 的媒体安全槽，新的 Call Request 只能得到 `OWNER_BUSY`。自托管 LiveKit 对已签发 token 不具备同等即时撤销能力，因而不能满足这项 V1 硬约束；但 LiveKit Cloud 也尚无中国大陆可用性承诺，仍只是待大陆实测的媒体候选，不能在验证前锁定。正式媒体部署必须同时通过活动撤销、预加入撤销和中国大陆网络验收。详见 [LiveKit Token 撤销与设备即时撤销边界](../research/livekit-token-revocation-and-immediate-device-revocation.md) 与 [LiveKit Cloud 中国大陆网络与成本闸门](../research/livekit-cloud-mainland-network-and-cost-gate.md)。
