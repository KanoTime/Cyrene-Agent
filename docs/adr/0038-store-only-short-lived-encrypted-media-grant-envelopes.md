# 只暂存短时加密的媒体加入资料信封

> 状态：Owner 已于 2026-07-23 接受。V1 采用方案 A 的受信公网控制面，并允许为适配无状态云函数，在数据库中短时保存不可直接使用的加密信封；明文 LiveKit Token 与 Call E2EE Key 仍绝不持久化。

## 背景

CloudBase 云函数实例彼此不共享状态，且实例会按负载创建、冻结与销毁。手机和桌面分别领取 Media Join Grant 时不能依赖同一函数实例的进程内存。若继续坚持“任何形态都不进入持久层”，则只能依赖不可靠的实例复用、额外部署有状态服务，或提前引入 V1 已暂缓的端点设备公钥生命周期。

V1 已明确选择方案 A：公网控制面是短暂可读每通共享 E2EE 密钥的受信组件。因此，在同一信任域中使用控制面主密钥加密的短时信封，不扩大能够读取明文的主体；它只改变无状态调用之间的可靠交接方式。

## 决定

Voice Call 进入 `CONNECTING_MEDIA` 后，控制面生成每通独立的随机 Call E2EE Key、两个 call-scoped LiveKit Token，以及手机、桌面各自独立的 Media Join Grant。每份 grant 立即以 AES-256-GCM 加密为端点专属信封，数据库只保存：

- 信封版本、随机 nonce、密文与认证标签；
- 对应 Voice Call、指定端点和领取截止点；
- 是否已领取的单次消费状态。

主密钥只存在于正式云函数的生产环境变量中，不进入代码、客户端、数据库、日志、审计、URL、二维码或错误正文。信封最长保留 30 秒；指定端点成功领取后立即清除其信封，两个端点均领取、电话终态、撤销、超时或授权重建时清除全部剩余信封。领取响应设置 `no-store`，明文 grant 只进入当前 HTTPS 响应和端点内存。

加密使用带上下文绑定的 AES-256-GCM；附加认证数据至少绑定信封版本、Call ID、端点 Device ID、端点类别和截止点。任何解密、认证、端点匹配、过期或重复领取失败都 fail-closed，电话不得以未加密媒体继续。

## 后果

- 可以在 CloudBase 无状态、多实例调用之间可靠地让两个端点各领取一次资料，而不增加新的常驻服务或要求重新配对。
- 数据库泄露本身不能直接得到 Token 或 E2EE 密钥；若数据库与控制面主密钥同时泄露，攻击者仍可能在 30 秒窗口内解密未消费信封。这与方案 A 已接受的“控制面受信可读”边界一致，但不能声称控制面零知识。
- 原有“密钥或 Token 绝不以任何形式进入数据库”的表述由本 ADR 精确替换为“明文绝不进入数据库；只允许本 ADR 定义的短时端点专属加密信封”。
- 方案 B 的端点公钥密封仍是未来更强边界；若采用，需要独立设计配对认证、公钥替换、轮换、撤销与恢复，不得把本信封主密钥机制描述为端到端零知识。
